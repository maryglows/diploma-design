# GitHub для диплома: инструкция с нуля

Подготовлено 22.10.2026. GitHub здесь используется как папка проекта с историей изменений. Устанавливать Git и работать в терминале на первом этапе не нужно.

## 1. Что означают слова

| Слово | Простое объяснение |
|---|---|
| Git | Система, которая записывает историю файлов |
| GitHub | Сайт, где размещают Git-репозитории и обсуждают работу |
| Репозиторий | Весь проект: файлы, история и настройки доступа |
| README.md | Первая страница проекта; .md — текст в формате Markdown |
| Commit | Сохранённая порция изменений с описанием |
| main | Основная ветка, где находится принятая версия |
| Ветка | Отдельная линия изменений; исходные файлы main не меняются до объединения |
| Pull request (PR) | Предложение внести изменения из одной ветки в другую; видно сравнение версий |
| Merge | Объединение изменений, например из ветки агента в main |
| Issue | Карточка задачи или вопроса |
| Milestone | Группа задач к этапу; может иметь дату выполнения |
| Projects | Дополнительная доска задач; на старте можно обойтись без неё |

В GitHub файлы, Issues и Projects — разные инструменты. Сам диплом храним в репозитории, задачи сначала в TASKS.md. Не нужно осваивать всё одновременно.

## 2. Создать новый закрытый репозиторий

1. Войти в нужный GitHub-аккаунт и открыть https://github.com/new.
2. В поле Owner выбрать свой аккаунт. На присланном скриншоте владелец старого репозитория — mekaev; подключённый к этому чату аккаунт — maryglows. Это разные имена: перед созданием проверить, куда сохраняется новый проект.
3. Repository name: `diploma-design`.
4. Description: `Диплом по промышленному дизайну: исследования, консультации, задачи и материалы`.
5. Visibility: **Private**. Доступ будет у владельца и у тех людей/приложений, которым он его предоставит.
6. Включить README. Лицензию можно пока не выбирать. Создать репозиторий.

Старый mekaev/salut изменять не нужно: он относится к другому проекту.

## 3. Загрузить стартовый набор

1. Распаковать Diploma_GitHub_starter.zip на компьютере.
2. Открыть внутри папку diploma-design.
3. В новом репозитории выбрать Add file → Upload files.
4. Перетащить **содержимое** папки diploma-design: README.md, PROJECT.md, папки и прочее. Не загружать только ZIP и не создавать лишний внешний уровень папки diploma-design внутри репозитория. Скрытый .gitignore можно добавить отдельно позднее, если система его не показывает.
5. Проверить, что существующий README будет заменён нашей стартовой страницей.
6. Написать описание сохранения: `Добавлены материалы диплома и план исследования`.
7. Для этой начальной загрузки выбрать сохранение прямо в main и нажать Commit changes.
8. Открыть README и проверить ссылки на TASKS.md, исходную консультацию и презентацию.

Веб-загрузка GitHub допускает файл до 25 MiB и до 100 файлов за раз. Этот набор укладывается в эти пределы. Проверка относится к содержимому архива, а не к размеру самого ZIP. Если браузер не передаёт папки, использовать браузер с поддержкой перетаскивания папок или загрузить их через GitHub Desktop позже.

## 4. Подключить агента

Ссылка на private-репозиторий сама по себе не даёт приложению доступа. В используемом подключении GitHub нужно разрешить именно новый репозиторий. Если приложение показывает список репозиториев, выбрать diploma-design; если его нет, проверить разрешения подключения. Настройка зависит от того, в каком интерфейсе запускается агент.

Для начала новой рабочей сессии:

> Работаем с моим дипломом в [ссылка на репозиторий]. Прочитай AGENTS.md, PROJECT.md, CURRENT.md, TASKS.md и последнюю консультацию. Скажи, какой сейчас этап и какие три ближайшие задачи. Не назначай неизвестные дедлайны. Затем помоги выполнить DIP-002. Если доступа к файлам нет, сообщи об этом.

Codex читает AGENTS.md при работе в репозитории. Другим агентам можно явно поручить его прочитать. Этот файл задаёт правила, но не синхронизирует автоматически все разговоры из разных чатов.

## 5. Работа после каждой консультации

1. Сохранить запись или расшифровку. Для текста использовать файл meetings/raw/ГГГГ-ММ-ДД_topic.md. Если дата неизвестна, указать unknown-date; номер встречи тоже подходит.
2. Не переписывать исходник. Разбор сохранить отдельно в meetings/reviews/ по шаблону.
3. Попросить агента выделить требования, изменения, задачи, сроки и неясности; привязать выводы к временным отметкам.
4. Обновить TASKS.md, CURRENT.md и принятые решения в DECISIONS.md.
5. Проверить, что просьбы преподавателя не перепутаны с идеями помощника, а дата загрузки не стала датой встречи.
6. Сохранить изменения с описанием: `Разобрана консультация: уточнены пользователи и задания`.

Для крупных аудио и видео удобнее хранить в репозитории расшифровку и ссылку на оригинал в своём хранилище. Проверить доступ по этой ссылке отдельно: private-репозиторий не делает внешний файл закрытым. Не загружать в диплом посторонние персональные документы.

## 6. Когда нужны ветки

В одиночной работе простые загрузки можно сохранять в main. Когда агент меняет несколько материалов, удобен цикл:

1. Агент создаёт ветку, например research/users-comparison.
2. Вносит изменения и сохраняет commits.
3. Открывает PR в main с объяснением, что сделано.
4. Автор читает Files changed, проверяет содержание и замечания.
5. По решению автора изменения объединяются в main. Закрытый без объединения PR не добавит их в main.

PR — это не обязательная «сдача» преподавателю, а инструмент проверки изменений. GitHub показывает историю текста; PDF и PPTX обычно сравниваются хуже, поэтому сохранять важные объяснения и выводы в .md. Изменение большого бинарного файла может увеличивать размер истории даже при замене старой версии.

## 7. Задачи и дедлайны

На старте достаточно TASKS.md. Позже можно создать Issues для DIP-002 и других задач, перенести туда статусы и добавить milestone «Промежуточный просмотр». Дату milestone задать только после подтверждения календаря. В TASKS.md оставить ссылки и отметить перенос.

GitHub не устанавливает дедлайны по смыслу беседы сам. Агент должен извлечь подтверждённую дату, а неизвестную уточнить. Уведомления, календарь и автоматические напоминания настраиваются отдельно.

## 8. Где пределы

- Репозиторий удобен для текста, источников и умеренных по размеру материалов. Это не безлимитный диск.
- Более 100 MiB обычный Git не принимает; для больших файлов нужен Git LFS или внешнее хранилище. Для LFS сначала настроить рабочий процесс, а не просто загружать файл через сайт.
- История сохраняет прошлые версии. Удаление файла из текущей папки не стирает его из истории.
- Правила AGENTS.md помогают сохранять контекст, если агент получил доступ к актуальным файлам. Они не заменяют сохранение результатов в репозиторий.
